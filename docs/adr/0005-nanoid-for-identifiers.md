# 0005. 識別子に nanoID を用いる

ステータス: 受理
日付: 2026-05

## 背景

課題などのエンティティに識別子を振る必要がある。
識別子は URL に露出する。生成方式を決める必要がある。

## 決定

課題などの識別子に nanoID を用いる。
連番 (オートインクリメント) は採用しない。

## 理由

### 連番は推測できる

連番 ID は URL に露出すると推測の手がかりになる。
/task/5 が存在すれば /task/6 の存在は自明であり、
ユーザーは URL の数字を書き換えるだけで、未着手の先の課題に到達できてしまう。

これはアンロック導線と、課題を段階的に積み上げる学習体験を破壊する。
「やろうと思えばできてしまう」状態そのものが誘惑である。

### 誘惑を構造で取り除く

nanoID は推測不能なランダム文字列であり、次の課題の ID を予測できない。
「ズルする方法」を技術選定の段階で存在させない。
これは「ズルしないで」と意志に訴えるより、確実で、かつ優しい。

yutori が「主体性を返す」一方でこうした誘惑を取り除くのは、矛盾ではなく補完である。
ユーザーが学ぶことに集中できるよう、無意味な誘惑はあらかじめ設計者が取り除く。
意志の力を、くだらない誘惑との戦いに消耗させない。

## 検討した代案

### UUID

UUID も推測不能であり、誘惑を防ぐ目的は達せられる。
しかし URL に乗せたとき長く、見苦しい。
nanoID は同等のランダム性をより短い文字列で実現するため、
URL に露出する識別子として優れる。

### 連番

最も単純で軽量だが、上記の通り推測可能性が学習体験を損なう。採用しない。

## 影響

- 課題の順序は ID ではなく orderIndex カラムが担う (関心の分離)。
  ID から順序の意味を排除することは、推測の手がかりを断つ点でも正しい。
- 全テーブルを nanoID で統一するか、URL に露出する課題まわりに限定するかは
  未決。一貫性を取るなら統一が望ましい。
