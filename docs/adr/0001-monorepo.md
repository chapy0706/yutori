# 0001. モノレポ構成を採用する

ステータス: 受理
日付: 2026-05

## 背景

yutori は、Web アプリケーション本体と、ユーザーコードを採点するエンジンという、
性質の異なる二つの主要素を持つ。両者をどう配置するかを決める必要がある。

## 決定

apps と packages を持つモノレポ構成を採用する。

- apps/web に Next.js 本体を置く。
- packages/grader に採点エンジンを置く。
- packages/sandbox に QuickJS-WASM ラッパーを置く。
- packages/contracts に共有の Zod スキーマと型定義を置く。

## 理由

採点エンジンと Web 本体は、寿命も関心も異なる。

採点エンジンは「コードとテストケースを受け取り、結果を返す」純粋な部品であり、
Next.js も DB も知らない。これを Web 本体から独立したパッケージに切り出すことで、
将来の CLI 版や別プロジェクトでの再利用に開いておける。

これは UNIX 哲学の「一つのことをうまくやる独立したプログラム」を、
パッケージ境界として物理的に表現したものである。

## 検討した代案

### 単一リポジトリ・単一パッケージ

すべてを apps/web の中に置く案。初期の構築は速い。
しかし採点エンジンが Next.js と密結合し、独立したテストや再利用が難しくなる。
yutori の中核である採点エンジンを、フレームワークと心中させたくない。

### 別リポジトリへの分割

採点エンジンを完全に別リポジトリにする案。独立性は最も高い。
しかし構想・設計フェーズの現段階では、共有する型 (contracts) の変更が
頻繁に発生する。リポジトリをまたぐ変更は手間が大きく、時期尚早と判断した。
将来、採点エンジンが安定したら再検討の余地はある。

## 影響

- ワークスペース管理のツール設定が必要になる。
- パッケージ間の依存方向を一方向に保つ規律が要る (contracts が最も内側)。
