# 0002. 採点に QuickJS-WASM を用いる

ステータス: 受理
日付: 2026-05

## 背景

yutori はユーザーが書いた JavaScript / TypeScript コードを実行し、採点する。
信頼できないコードを安全に実行する手段を決める必要がある。

## 決定

ユーザーコードの実行に QuickJS-WASM を用いる。
QuickJS-WASM は Web Worker 内でロードし、メインスレッドから隔離する。

## 理由

### サンドボックスの隔離強度

WASM の隔離は、線形メモリの分離によって生まれる。
WASM モジュールは閉じた線形メモリを持ち、その中のコードはホストのメモリに触れない。
これは言語の違いではなくメモリ空間の違いによる隔離であり、
ホストが何の言語で書かれているかに依存しない。

### QuickJS という選択

ユーザーコードが JS である以上、実行には JS エンジンが要る。
QuickJS は Fabrice Bellard による軽量な JS エンジンで、WASM 化しても 200KB 前後。
採点は「短いコードを毎回起動して走らせる」ワークロードであり、
長時間動作向けに JIT 最適化された V8 ではなく、起動の軽い QuickJS が適する。
用途とエンジンの設計が一致している。

### 無料枠との親和性

クライアント (ブラウザ) 側で実行が完結するため、サーバー負荷がほぼゼロ。
進捗のメタデータのみをサーバーへ保存するハイブリッド方式を採れる。

## 検討した代案

### サーバーサイドのサンドボックス (E2B / Judge0 / 自前 Docker)

本格的だが、無料枠を超えやすい。タイムアウトとセキュリティの管理も重い。
将来のスケール時に検討する。

### V8 ベースの実行

起動コストが採点ワークロードに合わず、WASM 化したときのサイズも大きい。

## 影響

- 採点ロジック (判定) は packages/grader、実行は packages/sandbox と層を分ける。
- 実行時間・メモリの制限は QuickJS のポリシー機能で実装する。
- JS 以外の言語に課題を広げる場合、言語ごとに WASM 実行モジュールを
  差し替える構造を将来検討する (関連: 第二フェーズの Go-WASM 解析レイヤー)。
