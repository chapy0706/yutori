# 0004. Zod を仕様記述言語として全面採用する

ステータス: 受理
日付: 2026-05

## 背景

yutori の採点は、競技プログラミング的な厳格な値一致ではなく、
仕様 (型・構造) への適合で合否を判定する。
この「仕様」をどう記述するかを決める必要がある。

## 決定

課題の仕様を Zod スキーマで記述する。
Zod を単なるバリデーションライブラリではなく「仕様記述言語」として位置づけ、
採点・出題 UI・課題作成のすべてが同一のスキーマを参照する。

## 理由

### 仕様一致という採点方針

実世界のソフトウェアは「正解の集合」を相手にする。
ユーザー ID を生成する関数の正解は無数にあり、揃えるべきは特定の値ではなく
「形式に従っている」「型が正しい」という仕様である。
これは Design by Contract (関数を入力の事前条件と出力の事後条件の契約とみなす
考え方) の現代的な実装にあたる。

### 判定原理の統一

Zod を用いると、すべての判定が「スキーマに通るか」という一つの原理に統一される。

- 乱数を含む関数: 値ではなく形式・範囲を見る (z.string().uuid() など)
- 時刻を含む関数: 値ではなく型を見る (z.date() など)
- 値の厳密一致が必要な特例: スキーマに .refine() で値制約を追加する

判定エンジンが特殊ケースを持たなくなる。これは UNIX 哲学の
「一つのことをうまくやる」の応用である。

### 仕様の一元化

同一の Zod スキーマを、採点だけでなく出題 UI の仕様表示にも、
課題作成時の定義にも流用できる。仕様が一箇所に集中する。
これはクリーンアーキテクチャの依存方向の制御とも整合する。

## 検討した代案

### 独自の仕様記述フォーマット

JSON などで独自の仕様フォーマットを定義する案。
自由度は高いが、パーサもバリデータも自前で実装する必要がある。
Zod は TypeScript の型推論と統合されており、車輪の再発明を避けられる。

### 値の一致による採点 (競技プログラミング方式)

正解がひとつに収束する問題にしか適用できず、
ゲーム課題の多くが持つ「出力の揺らぎ」を扱えない。yutori の方針に合わない。

## 影響

- 課題定義は contractSchema として Zod スキーマを持つ (スキーマ確定済み)。
- packages/contracts が全パッケージから参照される最も内側の層になる。
- 課題作成者は Zod を書けることが前提になる。
