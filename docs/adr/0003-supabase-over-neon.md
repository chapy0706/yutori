# 0003. Neon ではなく Supabase を採用する

ステータス: 置換 (Superseded by ADR 0008)
日付: 2026-05
置換日: 2026-06-07

> この決定は ADR 0008 (Oracle Cloud A1 + Coolify セルフホスト構成への移行) によって
> 置換された。Oracle Cloud A1 を取得したことで、商用制限がなくコストゼロの
> セルフホスト構成が可能になり、Supabase 採用の前提が変わったため。
> 当時の判断記録として本 ADR は残す。

## 背景

yutori は無料枠で MVP を構築する。
データベース、認証、アセット (WebP 等) の配信が必要になる。
データ層のインフラを決める必要がある。

## 決定

DB・認証・ストレージの基盤として Supabase を採用する。
ORM には Drizzle を用い、Supabase の PostgreSQL に接続する。

## 理由

yutori が必要とするのは、データベース単体ではない。
ユーザー認証 (ログイン)、課題進捗の保存、WebP などアセットの配信、
これらすべてが要る。

Supabase は「Firebase のオープンソース代替」を出自とする統合プラットフォームで、
中核の PostgreSQL に加え、認証・ストレージ・リアルタイム購読を備える。
これらが一つの無料枠に収まる。

Drizzle は Supabase の PostgreSQL にそのまま接続できるため、
ORM の選択を犠牲にしない。

## 検討した代案

### Neon

Neon は「PostgreSQL そのもの」を出自とするサーバーレス DB。
ストレージとコンピュートを分離した設計で、DB としては優れている。
しかし提供するのは DB のみで、認証は別途 (Auth.js 等)、
ストレージも別途構築する必要がある。
部品を自前で集める構成は疎結合という点では美しいが、
MVP の構築工数としては重く、現段階では見合わないと判断した。

## 影響

- 認証は Supabase Auth に依存する。users テーブルは
  Supabase Auth の user id を参照する薄い存在とする。
- アセット配信は Supabase Storage を用いる。
- 将来 DB のみを切り出したくなった場合、PostgreSQL 同士であるため
  Neon への移行は比較的素直に行える。この移行可能性は維持しておく。
- Vercel Hobby プランは商用利用が不可。収益化時には有料プランへ移行する。
