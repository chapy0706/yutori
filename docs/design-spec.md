# yutori 設計仕様書

ゲーム制作で学ぶプログラミング学習サービス

バージョン: 0.5 (構想フェーズ)
最終更新: 2026-06-07

サービス名 yutori について:
「ゆとり」は、空間や時間に余白があること、詰め込まないことを指す言葉である。
焦らず、自分の好きな時間で、コツコツ学ぶ。その思想を名前に掲げる。
本書の設計判断に迷ったときは「それは yutori な選択か」と問い直す基準とする。

---

## 1. このドキュメントについて

本書は、ゲーム制作を題材としたプログラミング学習サービス yutori の設計意図を
記録するものである。「何を作るか」だけでなく「なぜそう設計したか」を残すことを
主目的とする。本書は yutori のドキュメント体系の中核 (思想と全体像の本体) に
あたる。

### ドキュメント体系

| ドキュメント | 役割 |
|--------------|------|
| README.md | リポジトリの顔。yutori が何で、なぜ存在するかの入り口 |
| docs/design-spec.md | 本書。設計の思想と全体像 |
| docs/directory-structure.md | ディレクトリ構成の詳細 |
| docs/glossary.md | yutori 固有の用語集 |
| docs/adr/ | アーキテクチャ決定記録。個別の決定を一枚ずつ記録 |

本書が「全体像」を語るのに対し、ADR は「一つの決定」を、
代案や却下理由まで含めて深く記録する。本書中の重要な決定には、
対応する ADR 番号を併記している。

## 2. サービスのコンセプト

### 2.1 一行で言うと

実在のゲーム (テトリス、どうぶつの森、スマブラのような体験) を、課題を解きながら少しずつ完成させていく、プログラミング学習サービス。

### 2.2 サービスが伝えたいこと

学ぶことは本来楽しい。作ることは本来楽しい。
このサービスは「楽しさを上乗せする」のではなく、「学習の楽しさを邪魔しているノイズを徹底的に除去する」ことを設計思想の中心に置く。

### 2.3 既存サービスとの違い

既存のプログラミング学習サービスは、おおむね次のいずれかの文化を持つ。

- 競技プログラミング系: 厳格な値一致による採点。正解は一つ。
- ステップ学習系: 答え合わせ文化。先に進むことが目的化しやすい。
- スキルチェック系: 評価が目的。学習過程への伴走は薄い。

本サービスは「優しい厳しさで、仕様思考を育てる」というポジションを取る。
このポジションは既存サービス群の中で空いている。

## 3. 設計を貫く思想

ここまでの設計判断は、すべて次の二つの原則から導かれている。

### 原則1: 主体性をユーザーに返す

- 音 (BGM/SE) はデフォルト OFF。鳴らすかどうかはユーザーが決める。
- アニメーションは OS の prefers-reduced-motion を尊重する。
- ランキングは表示 ON/OFF を選べる。誰と比べるかはユーザーが決める。
- ヒントは答えを与えず問いかけの形にする。答えはユーザーが出す。
- AI の使用は強制も推奨もしない。自己責任・自己管理に委ねる。

### 原則2: 認識は丁寧に、正確に渡す

- コントロールはユーザーに渡すが、フィードバックは惜しまない。
- 「ここまでは合っている」という事実を必ず明示する。
- 進捗はリアルタイムに、観点単位で可視化する。
- 称賛は行わない。演出された称賛は信頼を壊すため、事実の正確な提示に徹する。

この二原則は、過去にプログラミング学習で挫折・疲弊を経験した人への配慮から来ている。
設計判断に迷ったときは、この二原則に立ち返って決定する。

## 4. 教育設計

### 4.1 逆向き設計 (Backwards Design)

最終ゴールを先に定義し、そこから逆算してカリキュラムを組む。
「基礎を積み上げて最後に応用する」順向き設計は採用しない。
ユーザーに「この課題を作る意味があるのか」と一瞬でも思わせないことを、設計目標とする。

ゴール提示は三階層で行う。

| 階層 | 対象 | 提示方法 |
|------|------|----------|
| Level 1 | コース全体のゴール | 完成版ゲームを実際にブラウザでプレイさせる |
| Level 2 | 章のゴール | その章の完了状態を示すアニメーション |
| Level 3 | 課題のゴール | この課題で何が増えるかを Before/After で示す短い WebP |

### 4.2 段階的詳細化と Walking Skeleton

各コースは、最初の課題で「機能は薄いが端から端まで動く骨組み」を完成させる。
最初の課題が終わった瞬間、画面に「自分の作品の卵」が表示される状態をつくる。
最後の合体まで報酬が来ない構造を避ける。

テトリスコースの課題分割例:

1. 黒い画面に静止ブロックが1個表示される (Walking Skeleton)
2. ブロックが落下する
3. 矢印キーで左右に動く
4. 回転する
5. 床に着いたら止まる
6. 新しいブロックが生成される
7. 以降、ライン消去・スコア表示など

### 4.3 テストの5観点

採点は「同じ問題への大量のエッジケース」ではなく「観点の異なるテストの積み重ね」で行う。
テストは正解を選別する篩ではなく、学習者の理解状態を映す鏡である。

| 順序 | 観点 | 確認内容 |
|------|------|----------|
| 1 | 構造観点 | 期待された名前で関数がエクスポートされているか |
| 2 | 契約観点 | 引数と戻り値の型が仕様通りか |
| 3 | 基本観点 | ごく単純な入力で動くか (短時間のスモークテスト) |
| 4 | 仕様観点 | 仕様で明示された振る舞いが揃っているか (複数) |
| 5 | 頑健観点 | 不正入力や空入力で壊れないか (任意) |

観点は上から順に確認し、失敗した時点で以降を実行しない (チェックポイント方式)。
画面には「どの観点まで通過したか」をリアルタイムに表示する。

### 4.4 仕様一致による採点

競技プログラミング的な厳格値一致は採用しない。
実世界のソフトウェアは「正解の集合」を相手にする。
判定の軸は「特定の値に一致するか」ではなく「仕様 (型・構造) に適合するか」とする。

- 乱数を含む関数: 値ではなく、形式や範囲が仕様通りかを見る。
- タイムスタンプを含む関数: 値ではなく、型が仕様通りかを見る。
- 出力に揺らぎがあっても、型・構造が仕様に合致していれば合格とする。

仕様は Zod スキーマで記述する。Zod を「仕様記述言語」として全面採用する。
これにより、出題 UI への仕様表示、採点、課題作成のすべてが一つのスキーマを参照できる。
値の厳密一致が必要な課題に限り、スキーマに `.refine()` で値制約を追加する。

## 5. 採点アーキテクチャ

### 5.1 サンドボックスの層構造

```
4. テストハーネス層     自作  テスト注入・結果収集・判定
3. サンドボックスポリシー層  自作  リソース制限・API公開制御
2. QuickJS-WASM エンジン層  借用  ユーザーJSコードの実行
1. Web Worker 隔離層    ブラウザ  メインスレッドからの分離
```

JS エンジンそのものは自作しない (QuickJS-WASM を利用する)。
設計の主対象は層3 (ポリシー) と層4 (ハーネス) である。

### 5.2 WASM 隔離に関する整理

WASM の隔離強度は、言語の違いではなく線形メモリの分離によって生まれる。
ホストが Next.js/TypeScript であることは、サンドボックスの隔離強度に影響しない。
ユーザーコードを実行するのは Next.js ではなく、その内側で動く WASM モジュールである。

### 5.3 採点パイプライン

```
提出
 -> Biome 検査          構文 NG ならリンタ出力をヒントとして返却
 -> 過去課題の整合性チェック  OK ならユーザーコード採用 / NG なら模範実装に差し替え + 警告
 -> 仮想ファイルシステム構築  サンドボックス内に過去ファイル + 今回対象ファイルを配置
 -> 構造観点テスト
 -> 契約観点テスト
 -> 基本観点テスト (短時間スモーク)
 -> 仕様観点テスト群
 -> 頑健観点テスト
 -> 合否確定 + 詳細レポート
```

各観点の通過/失敗は Web Worker から postMessage でメインスレッドに逐次通知する。
進捗ストリームと最終判定は分離する。Worker は「何が起きたか」を構造化して流すだけとし、
合否や表示判断はホスト側に委ねる。これにより将来 CLI 版など別 UI への流用が容易になる。

### 5.4 時間制限

時間制限は二つの役割を持つ。

- 実行の打ち切り (無限ループからの保護)
- 性能を学習対象として明示する (速さも仕様の一部であると教える)

制限値は課題ごとに変える。何を測るための制限かを課題定義に言語化しておく。
パズル系のロジック関数は秒単位、対戦ゲームの1手は100ミリ秒単位など、ドメインに応じて設定する。
実装は QuickJS の interrupt handler に時刻チェックを仕込む。

### 5.5 Go-WASM の位置づけ (第二フェーズ)

第一フェーズは QuickJS-WASM のみで採点を成立させる。
Go-WASM は第二フェーズで「解析レイヤー」として追加する。

- 実行レイヤー: QuickJS-WASM がユーザーの JS を走らせて出力を得る。
- 解析レイヤー: Go-WASM が AST 解析・静的検査・コードメトリクスを担う。

Go 1.24 のリアクターモード (go:wasmexport + WASI reactor) は、
一度初期化したら関数を何度でも呼べる常駐モジュールを可能にし、採点ワークロードと相性が良い。
ただし境界でポインタを渡せない制約があり、文字列・構造体の受け渡しにグルーコードが必要になる。
このコストがあるため、MVP では採用しない。

将来 JS/TS 以外の言語の課題を作る場合、言語ごとに WASM 実行モジュールを差し替え、
解析・判定の Go レイヤーを共通化する構造を想定する。第二フェーズ設計時にこの絵を描く。

## 6. 課題とコースのデータモデル

```
Course (例: テトリスコース)
  finalSpec       ゴール仕様 (Zod)
  codeSkeleton    共通の骨組みファイル群
  tasks: Task[]
    id, order
    description     この課題で何を作るか
    targetFiles     この課題で評価対象となるファイル
    contractSchema  Zod スキーマ (仕様観点)
    timeBudgetMs    時間制限
    testCases       5観点それぞれのテスト群
    hints           観点ごとのヒント辞書
    referenceImpl   模範実装 (ハイブリッド合成用)
    goalMedia       Level 3 ゴール提示用 WebP
```

Course が最終ゴールを保持し、Task がその到達経路上の一段を表す。
各 Task は前の Task の完了を前提にでき、依存関係は order で線形化する。

### 6.1 コードの積み上げ方式 (ハイブリッド)

「ユーザーから見える世界」と「テストが対象とする世界」を分離する。

- ユーザーから見えるエディタ上のコードは、常にユーザー自身が書いたものを保持・表示する。
- テスト実行時、サンドボックス内の仮想ファイルシステムでのみ、過去課題のコードを扱う。
  - 過去課題のコードが Zod 仕様を満たす場合: そのまま使う。
  - 満たさない場合: 模範実装に差し替えてテストを続行し、ユーザーに警告を出す。
- 課題ごとの評価対象は targetFiles に限定する。理想はファイル単位での課題分割とし、
  過去のファイルを壊すリスクを構造的に減らす。

この設計により、過去課題のリグレッションが新規課題のテストを巻き添えにしない
(優雅な劣化)。ただし「過去課題が壊れている」事実は隠さず、戻って直すよう優しく促す。
これはリファクタリングという概念を自然に教える機会にもなる。

コース完走時には、ユーザー自身が書いたコードだけを結合した「自分版の作品」を
別途ダウンロードできるようにする。これを完走報酬とする。

## 7. フィードバック設計

### 7.1 失敗の表現

失敗は罰ではなく対話として表現する。
コンパイラエラーを対話的な手がかりとして示す思想 (Elm, Rust のエラーメッセージ) に倣う。

失敗表示の構成要素:

- 通過した観点を明示する (「ここまでは合っている」)。
- 期待値と実際値を冷静に並べる。
- ヒントは命令形ではなく問いかけの形にする (「もしかして〜?」)。
- 進捗は「2/5 失敗」ではなく「1/5 通過、次は2つ目」とフレーミングする。

業務のコードレビューの、より優しいバージョンを目指す。
業務レビューが省略しがちな「ここまでは良い」を、本サービスでは必ず明示する。
これは演出ではなく、事実の正確な伝達である。

### 7.2 ヒントの生成方式 (ハイブリッド)

| 方式 | 内容 | 使いどころ |
|------|------|------------|
| テスト固有ヒント | 各テストに onFail メッセージを持たせる | 主軸 |
| パターンマッチング | エラー型に対するヒント辞書 | 穴埋め |
| リンタ委譲 | Biome の出力をそのままヒントに | 初期の構文チェック段階 |

### 7.3 称賛は行わない

称賛システムは採用しない。
演出された称賛は、見抜かれた瞬間に信頼を破壊するため。
代わりに「ここまでは合っている」という事実の提示に徹する。
事実は演出ではないため、信頼を壊さない。解釈は学習者本人に委ねる。

### 7.4 用語辞書 (好奇心への応答)

本のアイコンからいつでも開ける、課題の概念をまとめた辞書を持つ。
7.1-7.3 が「失敗への応答」であるのに対し、この辞書は「好奇心への応答」である。
両者は性質が異なるため、節を分けて記述する。

#### 辞書の役割

辞書は、つまずいた人を救済する仕組みではない。
「もっと知りたい」「根本から理解したい」という好奇心への応答である。
したがって失敗の検知やヒントの強さの出し分けは行わない。
本のアイコンからいつでも開け、全ユーザーに同じ内容を見せる。

課題は辞書なしで解けることを前提とする。辞書は必須ではなく、
yutori のエンドコンテンツとして位置づける。全ユーザーの 1 割が
使えば十分という想定で設計し、万人に媚びないことで深さの純度を守る。

#### 担当する深さの帯

学習内容を 0 から 10 で表すと、各要素の担当は次のように分かれる。

| 帯 | 内容 | 担当 |
|----|------|------|
| 0-1 | なぜそもそもこの概念が存在するのか (根本理解) | 辞書 |
| 3-7 | 課題を解くのに使う、よく使う中核部分 | 課題本体 |
| 8-10 | この概念の応用、その先の発展 | 辞書 |

課題本体は 3-7 を、ごちゃごちゃさせずに渡す。壁にぶつかる余白を残す。
0 から 10 まで教え込む学習は「いま何の役に立つか分からないものを信じて
覚えろ」と要求し、心を挫く。yutori は必要になってから学ぶ
ジャストインタイム学習を採る。辞書は壁にぶつかった人が初めて開く場所である。

#### 辞書はユーザーを外に送り出す

辞書は知識を与えきらない。検索のフックとなるキーワードと、
公式ドキュメントへの導線を渡す。
初学者が検索できない最大の理由は、その概念の名前を知らないことである。
名前を知らないものは検索窓に打ち込めない。
辞書が概念の名前という鍵を渡すことで、世界中の情報がその人の前に開ける。
辞書は知識の終着駅ではなく、乗り換え駅である。

#### ソートによる抽象化のトレーニング

辞書はその課題に登場する全概念を、順序なく並べる。
ユーザーが自分でソートする (テーマ別・目的別など)。

ソート結果には、目的の中心となる概念だけでなく、少しずれた
「想定外の隣人」も意図的に含める。中心概念だけが出てくる正確な検索では
発見が起きない。少しずれた隣人がいるからこそ「これも仲間なのか」という
驚きが生まれ、ユーザーは自分で概念を抽象化する。

複数の切り口で同じ概念に出会ううちに、その概念は知識のネットワーク
(スキーマ) の結節点になる。初学者の点状の知識が、熟達者のネットワーク状の
知識へ組み変わる。ソートという遊びが、抽象化のトレーニングになっている。
これはセレンディピティ (探していないが価値あるものに出会う幸運) の設計である。

詳細な設計判断は ADR 0007 を参照。

## 8. 進捗の可視化と他者の存在

### 8.1 草 (コントリビューショングラフ)

ログイン時、直近の学習進捗を GitHub のコントリビューショングラフのように表示する。
他者の存在を意識し、切磋琢磨のきっかけとすることが目的。

草に積む指標は提出回数だけにしない (数稼ぎを避けるため)。
合格課題のユニーク数、累計編集行数、連続学習日数などを組み合わせる。

### 8.2 ランキングの設計原則

「追いつけなくて諦める」を構造的に防ぐ。
社会的比較理論では、比較対象が自分の射程内にあると鼓舞になり、遥か上だと諦念になる。
したがって、学習者には「射程内の他者」だけを見せる。

- 全体ランキングは表示しない。
- 並走者表示: 進度の近い数人を「いま似たペースで進んでいる人」として自動表示する。
- 変化量表示: 絶対値ではなく「今週増えた合格数」など変化量を見せ、始点を平等にする。
- 多軸表示: 速さ・挑戦回数・コードの短さなど複数軸を持ち、どこかで輝ける構造にする。
- ランキング表示そのものを ON/OFF できる。比較したい時だけ比較する主体性を返す。

## 9. ゲーム性と報酬設計

### 9.1 エンタメ性は機能要件である

「作ることは楽しい」を肌で感じさせることを、明示的な機能要件とする。
楽しさとは学習の感覚である (A Theory of Fun)。本サービスは学習の楽しさを
邪魔するノイズを除去する立場であり、楽しさを上から塗装するゲーミフィケーションとは異なる。

### 9.2 Juicy な演出

提出からリザルトまでの一連の流れに、小さなフィードバックを丁寧に重ねる。
ただし過剰な賑やかさは避け、上質でミニマルなトーンを保つ。

- BGM / SE / アニメーション の3つを独立に ON/OFF できる。
- BGM・SE はデフォルト OFF。アニメーションは OS 設定 (prefers-reduced-motion) を尊重。
- 失敗音は否定的に響かせない。音でユーザーを罰しない。
- 無料音源を利用し、出典・ライセンスを assets 配下に集約管理する。

### 9.3 ログインボーナスと応援メッセージ

- ログインボーナス: 毎日同じものを配らず、変化と軽い予測不可能性を持たせる。
  連続ログインは強い義務にしない。途切れてもペナルティはなく、小目標が再設定されるだけ。
- 応援メッセージ: 3種類の固定文から1つを選び、並走者の誰かに送れる。
  固定文に限定することで、システムが文面の優しさを保証する。
  送ると送り手にもボーナス、受け手はログイン時に受信を楽しめる相互報酬とする。

### 9.4 アンロック設計 (Cosmetic only)

アンロックされるのは背景・アイコン・BGM・SE など、学習スペースの自己表現要素のみ。
ボーナスの取得有無は学習内容に一切影響しない (Pay to Win を避ける)。

- 取得方法: コイン購入 (日常的な楽しみ) と、課題・コース完走による直接獲得 (達成の記念) を併用。
- 完走報酬は自己表現と達成証明を兼ねる (例: コース完走者だけが持てる背景)。

### 9.5 ゲーム課題のアンロック導線

- 最初の非常に簡単なゲーム課題を完了すると、複数のゲームが一気にアンロックされる。
  「最初の課題で基本構文は身についた。だからどれでも作れる」という導線を表現する。
- アンロックは門番ではなく案内とする。先のゲームを作る義務は課さない。
- ロック中のゲームも「遊ぶ」ことはできる。
  プレイ可能なゴール提示として機能し、「次はこれを作りたい」という動機を生む。
  ロックされているのは「作る権利」であって「見る・遊ぶ権利」ではない。

### 9.6 「開きたい」を生む動機の設計

yutori は「勉強しに行く場所」ではなく「帰ってくる場所」を目指す。
そこへ人を引き寄せる動機を、次の原則で設計する。

#### 損失回避ではなく獲得期待

ユーザーを動かす感情には二種類ある。
「開かないと損をする」という損失回避と、「開くと良いことがありそう」という獲得期待。
yutori は後者のみを用いる。スタミナ制、ログインしないと損をする仕組み、
FOMO (取り残される恐怖) を煽る通知は採用しない。
これらは名前 yutori が掲げる「焦らせない」と正面から矛盾するため。

#### 変動報酬は、優しい強さで使う

報酬が予測不能なタイミングで得られると、その行動は強く繰り返される
(変動比率強化スケジュール)。SNS やソーシャルゲームはこの原理を最大出力で用い、
強力な依存と引き換えにユーザーを消耗させる。
yutori はこのエンジンを用いるが、出力のつまみ (希少さ・不確実性・間隔) は
意図的に控えめにする。引き込みの強さより、ユーザーが消耗しないことを優先する。

#### 中心に置く引力は「好奇心」

報酬のドキドキ (変動比率) と、続きが気になるワクワク (好奇心) は別種の引力である。
情報の空白理論によれば、人は「知っていること」と「知りたいこと」の間に
空白を感じると、それを埋めたくなる。好奇心型の引力は満たされると人を豊かにし、
消耗を生みにくい。そして好奇心は「学ぶことは楽しい」と同じ燃料で動く。
yutori が人を引き寄せる主たる引力は、報酬ガチャではなく、この好奇心とする。
引力の種類を、目的地 (学びの楽しさ) と一致させる。

#### 余白を設計する

全ての情報を提示しきらない。次に何が来るかを少しだけ隠すことで、
ユーザーの中に「想像のための空間」を残す。開いていないときも yutori を
想像している状態をつくる。これは名前 yutori の「ゆとり = 空白」とも一致する。
ただし、完全な空白は不意打ちになる。「何かが近づいている」という小さな気配を
置くことで、初めてユーザーは予想を始められる。気配は想像の着火点である。

### 9.7 デイリーガチャ

1日1回引けるガチャを用意する。FOMO の装置ではなく、生活リズムへの寄り添いとする。

- 水曜・土曜を確率アップの曜日とする。
  水曜は「仕事の中日」、土曜は「休日」に対応し、しんどい日・暇な日にそっと背を押す。
- 確率アップでない日に引いたユーザーが「損をした」と感じない演出にする。
  特定日をほんのり上げる足し算の演出とし、平日を下げる引き算の演出にはしない。
- ガチャの結果は学習内容に影響しない (9.4 と同じ Cosmetic only 原則)。
- 目玉となる景品は後述の期間限定イベント関連アイテム (期間延長・ヒント)。
  着せ替えアイテムも交換対象に含め、「これでもよい」という選択肢の幅を持たせる。

### 9.8 期間限定イベント (不定期出現課題)

学習の習慣化を促す、yutori で唯一「健全な悔しさ」を意図的に設計する機能。

#### 仕様

- 出現するのは、ユーザーが過去にクリアしたゲームの類似課題ゲーム。
- 通常課題と同じく、解かずに「遊ぶ」ことは可能。
- 課題として解く場合、説明はほぼ付けない。
  日頃の学習で理解できる内容をベースにするため、説明なしで成立する。
- 難易度は「日頃学習していないと、サラリとは作れない」水準に設定する。
- 出現は24時間限定。同一課題の再出現は3週間以上後とする。

#### 煽り文 (気配の設計)

- 出現の5日以内になると、ホーム等に煽り文が一言表示される
  (「次のゲームが増えました」とは別系統の予告)。
- 煽り文の出現後、2〜4日の幅をもって本開催される。
  この幅が「いつ来るか読みきれない」という余白を生む (9.6 参照)。
- 開催期間は24時間。

#### 設計意図

- ここで初めて「悔しい」という感情を設計に許す。
  yutori は全体として焦らせず責めない設計だが、一箇所だけ意図的に悔しさを置く。
- この悔しさが健全なのは、課題が「今までの学習で十分解ける」内容だから。
  能力不足で届かない悔しさは人を折るが、「やればできたのに習慣をサボった」
  悔しさは人を次へ向かわせる。悔しさの矛先を、能力ではなく習慣に向ける。
- 24時間制限と3週間の再出現間隔が、学習の習慣化を促す「壁」として機能する。
- AI の使用可否は通常課題と同じ (強制も推奨もしない)。
  AI を使う場合でも本人の工夫次第で解けるよう設計する。

### 9.9 ガチャ・通貨で得られるイベント関連アイテム

期間限定イベントに対して、ガチャや通貨交換で次のアイテムを得られる。

| アイテム | 効果 | 持続性 |
|----------|------|--------|
| 期間延長 | そのイベント課題の挑戦可能時間を延長する | その開催時のみ有効 |
| ヒント | そのイベント課題のヒントを表示する | 再出現時にも引き継がれる |

- 期間延長を「その時だけ」とするのは、習慣化を促す壁としての性質を保つため。
- ヒントを再出現時にも引き継ぐのは、一度向き合った課題への投資を無駄にしないため。
- これらに通貨を使わず、着せ替えアイテムに使ってもよい。
  どちらを選んでもよい、という選択の自由をユーザーに残す。

### 9.10 課題スキップアイテム (逃げの一手)

選択した課題を「クリアしたことにする」効果を持つ、特殊なアイテム。

#### 入手方式

- ストアの棚には並べる。ただし通貨では購入できない。
- 入手手段はデイリーガチャの低確率枠のみとする。
- 「見えるが、狙えない」状態を意図的につくる。
  ストアに並ぶことで「逃げ道は確かに存在する」と視認できる。
  通貨で狙えないことで、目的化・競争の的になることを防ぐ。

#### 出現制御

- 一度入手したユーザーには、使用するまでこのアイテムは再出現しない。
  逃げ道は一本あれば足りる。複数所持できると「ストックしておく資源」になり、
  使うタイミングを計算し始める。一枚に絞ることで、純粋な安心感だけが残る。
- 使用後は 3 ヶ月間、そのユーザーへの出現を制限する。
  逃げ道を使った経験そのものが、逃げ道の希少性を体感させる。
  「これは無限の抜け道ではなく、本当に困ったときの一回きりの手だ」と、
  説明ではなく体験で伝わる。
- 出現制限中も、ストアの棚からアイテムの存在を消しはしない。
  「次に巡り会えるまで、しばらく」といった気配だけを残す。
  制限を罰として見せず、希少性を伝える媒体として見せる (9.6 の気配の設計)。

#### 高額販売を採用しない理由

- 当初は破格の高額販売を検討したが、これは目的のすり替えを招く。
  高額にすると、ユーザーの意識が「学習」から「課金」「コイン稼ぎ」へずれ、
  安心装置だったはずのアイテムが「買うために頑張る目標」に変質する。
- アイテムの本質は「使わせること」ではなく「存在すること」にある
  (下記の設計意図参照)。高額販売はその存在をご褒美化し、思想と矛盾する。
- ガチャ低確率枠に置くことで、「ふいに出会うもの」という距離感を保ち、
  競争の対象にせず、安心感だけを純粋に残す。

#### 設計意図

- 用途を限定しない。「どうしても解けない」「苦手だから解きたくない」といった
  ネガティブな理由での使用も許容する。
- このアイテムの本質は「使わせること」ではなく「存在すること」にある。
  逃げ道が見えている部屋のほうが、人は落ち着いて長くいられる (心理的安全性)。
  「最終手段がある」という安心感が、かえってユーザーを学習に向かわせる。
- 「逃げの一手があるという心のゆとり」を演出する。これは名前 yutori と一致する。

### 9.11 ガチャ確率の動的調整 (裏設定)

デイリーガチャの当たり確率を、ユーザーのログイン状態に応じて静かに調整する。

- ログイン頻度が高いユーザー: 確率を上げる (日頃の利用への報酬)。
- ログインが久しぶりのユーザー: 確率を上げる (戻ってきたことへの歓迎)。

#### 設計意図

- 両端を上げる点が、一般的なソーシャルゲームの「離脱者引き止め装置」と異なる。
  これは引き止めではなく、「いつもありがとう」と「おかえり」の二つの歓迎である。
- 特に久しぶりのユーザーへの配慮が重要。久しぶりにアプリを開くとき、人は
  「サボっていた」という負い目を感じやすい。多くのアプリは「○日ぶりです」等の
  表示で無自覚に罪悪感を刺激する。yutori は逆に、戻ってきた人をそっと優遇する。
  戻ってきたことを、責めるのではなく迎える。
- この調整は表に出さず裏設定とする。明示すると押し付けがましくなるため。
  ユーザーは理由を知らないまま「今日はついていた」と感じる。
  日頃の報酬と捉えるか、恵みと捉えるかの解釈は、ユーザーの余白に委ねる (9.6)。

#### 注意 (調整幅)

- 久しぶりのユーザーの優遇が行きすぎると、理屈の上では「一度離れて戻るのが得」
  という歪んだ最適行動を生みうる。
- 確率の上げ幅は「気づかれない程度のそっとした恵み」に留める。
  大盤振る舞いにした瞬間、それは引き止めの装置に変質する。
  強さの加減が思想を守る (9.8 の「悔しさは一箇所だけ」と同じ原則)。

### 10.2 識別子の設計

課題などの識別子に、連番 (オートインクリメント) ではなく nanoID を採用する。

#### 連番を避ける理由

- 連番 ID は推測できる。URL に `/task/5` が現れれば、`/task/6` の存在は自明。
- ユーザーは URL の数字を書き換えるだけで、未着手の先の課題に到達できてしまう。
  これはアンロック導線 (9.5) と Walking Skeleton の段階的体験 (4.2) を破壊する。
- 「やろうと思えばできてしまう」状態そのものが誘惑である。
  鍵のかかっていないドアは、つい開けたくなる。

#### nanoID による解決

- nanoID は推測不能なランダム文字列であり、次の課題の ID を予測できない。
- 「ズルする方法」を技術選定の段階で存在させない。
  「ズルしないで」と意志に訴えるより、構造で守るほうが確実で優しい。
- yutori が「主体性を返す」一方で「無意味な誘惑を置かない」のは矛盾ではなく補完。
  主体性を尊重するからこそ、意志を試すような誘惑をあらかじめ取り除く。
- UUID も推測不能だが、nanoID はより短く URL に乗せても見苦しくないため採用。

#### 順序との分離

- 課題の順序は ID ではなく tasks.orderIndex カラムが担う (スキーマ確定済み)。
- ID から順序の意味を排除することは、推測の手がかりを断つ点でも正しい。
- ID は純粋な一意識別子に徹し、順序管理は別カラムに委ねる (関心の分離)。

### 10.3 インフラ

Oracle Cloud A1 (Always Free 枠・ARM aarch64) を取得済みであり、これを基盤とする
セルフホスト構成を採用する。当初の Vercel + Supabase 構成からの変更であり、
経緯と理由は ADR 0003 (置換済み) および ADR 0008 を参照。

| 領域 | 採用 | 役割 |
|------|------|------|
| ホスティング | Oracle Cloud A1 + Coolify | アプリ本体のデプロイ・運用 (PaaS) |
| 入口 | Cloudflare + Cloudflare Tunnel | DNS・TLS 終端・WAF。A1 を Tunnel 経由で公開 |
| リバースプロキシ | Traefik (Coolify 管理) | ホスト名で各コンテナへ振り分け |
| DB | PostgreSQL (A1 上・Coolify 管理) | アプリの主データ |
| 認証 | Keycloak (A1 上) + Auth.js | Keycloak を IdP とし Auth.js で委譲 |
| ストレージ | A1 ファイルシステム + Cloudflare 配信 | WebP・音源などの静的アセット |

#### 構成の要点

A1 はパブリック IP を持たない。外部からの到達は Cloudflare Tunnel 経由のみとし、
管理用 SSH は E2.Micro 踏み台 (MFA) を経由する別経路とする。攻撃面を最小化する設計。

TLS は Cloudflare で終端し、その南側 (Tunnel 内・Traefik・各コンテナ) はすべて
平文 HTTP で完結する。A1 にパブリック IP がなく Let's Encrypt の HTTP-01 チャレンジが
成立しないため、Traefik では TLS を扱わない。

アプリはインフラの詳細を知らない。接続情報 (DATABASE_URL、Keycloak の issuer URL 等) は
すべて環境変数で注入し、ホスト名や物理配置をコードに埋め込まない。これにより
インフラの変更がアプリのコードに波及しない。詳細は docs/a1-infra-reference.md を参照。

#### Supabase からの変更について

当初は Vercel + Supabase を採用していた (認証・DB・ストレージが一つの無料枠に
収まる利点から)。A1 を取得したことで、商用利用の制限がなく、本質的にコストゼロで、
インフラを自分で握れるセルフホスト構成が可能になった。本番運用は約半年後を
想定しており、その時期までに自前構成を育てる方針とする。

認証は Supabase Auth ではなく Keycloak + Auth.js を最初から採用する。
A1 を箱として持っている以上、Supabase で建てて後から移行する工程は無駄になるため。
クリーンアーキテクチャの依存性逆転により、認証実装は infra 層に閉じ込められ、
core 層は AuthGateway 等のポート越しに認証を扱う。将来認証基盤を変えても
core は無傷である。

### 10.4 ゴール WebP の自動生成パイプライン

Playwright の動画録画機能を用いて、各課題のゴール提示メディアを自動生成する。

```
1. タスク定義に scenario (操作手順・viewport・duration) を持たせる
2. CI で各タスクの模範実装をビルドし、Playwright で起動、scenario を実行して webm 録画
3. ffmpeg で webm をアニメーション WebP に変換 (GIF より軽量)
4. 前タスクと並べた Before/After 比較メディアも生成
```

課題追加が「タスク定義を書く」だけで完結し、デモメディアが自動で量産される構造とする。

## 11. 開発フェーズ

### フェーズ1 (MVP)

- QuickJS-WASM による採点の最小ループを通す (おもちゃ課題で骨格を検証)。
- サンドボックスポリシー (時間・メモリ制限、API 公開範囲) を設定ファイル化する。
- テトリスコース1本を、5観点テスト・ヒント・模範実装・ゴール WebP まで作り込む。
- 認証、進捗保存、草、並走者表示、ランキング ON/OFF。
- ログインボーナス、応援メッセージ、Cosmetic アンロックの基本系。

MVP はコース1本で十分。1本が体験として成立すれば差別化価値を実証できる。
